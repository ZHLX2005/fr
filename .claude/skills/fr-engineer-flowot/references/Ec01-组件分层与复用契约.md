# Ec01 — 组件分层与复用契约

> 适用范围：仅适用于 FR 项目（`D:\DevProjects\my\github\fr`）。E00 是 E 大序列总路由；样式方案见 Ea 子序列，主题与颜色治理见 Eb 子序列，**组件分层与复用判定**由本文件负责。
> 本文件是**判定契约**，不是组件清单——当前有什么组件、哪里在重复，见 [[Ec02-组件现状与收敛路线]]；**目录级位置地图**（什么组件住在哪、新组件放哪）见 [[Ec03-组件内聚位置]]。
> 全量证据见 `docs/architecture/component-reuse-audit.md`（2026-10-23 审计）。

## 何时使用

- 新写一个 widget 前，先判断它该放在哪一层、是否已有同形态的共享件。
- review 时看到「这段 UI 第 N 次出现」或「两个地方长得一样但颜色/尺寸不同」。
- 发现某个组件零引用、或两个模块各自实现了同一形态。
- 决定某个业务模块内的 widget 是「留在模块内」还是「下沉到共享层」。

## 1. 分层契约

FR 的 UI 代码按五层组织，上层可依赖下层，**下层不得反向依赖上层**：

| 层 | 位置 | 职责 | 硬约束 |
|---|---|---|---|
| **L1 token** | `lib/design_tokens/`（`radius.dart` / `spacing.dart` / `typography.dart` / `color/`） | 原始数值与色板 | 纯常量，不依赖 `BuildContext` |
| **L2 主题默认值** | `lib/core/theme/colors/strategy/*/themes/default.dart` | 从 token 派生语义色 | 只读 L1，不得引用组件 |
| **L3 语义契约** | `lib/core/theme/colors/strategy/*/`，`lib/core/theme/extensions/` | `ColorStrategy` 契约与 `ThemeExtension` 注入 | 只读 L1/L2；不得引用 L4+ |
| **L4 原子组件** | `lib/core/ui/atomic/`（`Base*`） | 单一形态、无业务语义的可复用件 | 只读 L1–L3；不得引用业务模块 |
| **L5 域内壳层 / 风格包** | `lib/core/ui/shell/`、`lib/core/ui/zen/`、**`lib/core/ui/game/`**（联机 UI 件统一聚合处） | 有领域语义的组合件与样式包 | 只读 L1–L4 与逻辑层；可被业务模块直接消费 |
| **L6 业务装配** | `lib/core/<模块>/`、`lib/lab/demos/<模块>/` | 页面与模块专属 UI | 不得把通用件定义在业务模块内 |

> **联机 UI 的拆分口径（2026-10-24 起）**：`lib/core/ui/game/` 承接全部**联机 UI 件**（就绪卡六件套、`GameLobbyPage` + `_lobby_form`、`BoardChatOverlay`、`EmojiPanel`/`EmojiOverlay`、`RelayConnectionBar`/`RelayConnectionStatusBadge`）；`lib/core/game_kit/` 只留**纯逻辑**（spec / slots / identity / skin / Lua 脚本 / 快照事件模型如 `emoji_snapshot.dart`）。依赖方向恒为 `ui/game/ → game_kit`，**禁止逻辑层 import UI**（反例已修：`chat_event.dart` 曾从 `emoji_overlay.dart` 导入事件模型，已抽为 `game_kit/emoji/emoji_snapshot.dart`）。

**层号标注的现状缺陷**：`// Layer N:` 注释目前**不可作为导航依据**——通用 `ColorStrategy` 契约标 Layer 1（`lib/core/theme/colors/strategy/color_strategy/color_strategy.dart`），chess/sudoku 的同名契约标 Layer 3，其 Default 实现又标 Layer 2。新增文件按上表标注；历史文件不做批量改写，但**不得据旧层号推断依赖方向**。

### 跨模块消费的落点规则

| 组件性质 | 落点 | 反例（现存） |
|---|---|---|
| 无领域语义的通用件 | `lib/core/ui/atomic/` | `RtRoundIconButton` 寄居 `remotetype/ui/`（应下沉） |
| 联机 UI 件（就绪卡 / 大厅页 / 聊天浮层 / 表情面板 / 连接条） | `lib/core/ui/game/` | 迁移前曾寄居 `game_kit/lobby|chat|emoji/` 与 `net_engine/relay_v3/`（2026-10-24 已聚合） |
| 联机逻辑件（spec / slots / identity / skin / Lua 脚本 / 快照模型） | `lib/core/game_kit/` | — |
| 仅本模块使用的形态 | 留在模块内 | `coup_lua` 的 6 人局手牌区——**这是正确的做法，不要下沉** |

> **判定口诀**：一个组件如果**换个模块还得用**，它就不该住在当前模块里。

## 2. 复用判定顺序（禁止跳步）

遇到「这个 UI 好像写过」的冲动时，按顺序走，**不得跳到第 4 步新建**：

1. **查已有清单**：读 [[Ec02-组件现状与收敛路线]]，确认 `lib/core/ui/atomic/`、`lib/core/ui/shell/`、`lib/core/game_kit/` 是否已有同形态件。
2. **查漏用**：已有实现但调用点没用的，**一律先改用**（这是最高收益的一类）。FR 当前最大的浪费不是「缺组件」，而是「有组件没人用」。
3. **查分叉**：同一功能在两处各写一份（尤其颜色来源不同），按**视觉分叉**处理，优先级高于纯重复。
4. **才考虑新建**：同形态在 ≥3 处出现、且确无共享实现时，新建到 L4 或 L5。
5. **下沉或留在原地**：模块内件若被第二个模块需要 → 下沉；否则留在模块内（教学性 demo 的规则/引擎代码尤其不要抽）。

### 触发重建的判据

| 情形 | 动作 | 依据 |
|---|---|---|
| 同形态 ≥3 处 | 抽共享件 | 收益随重复数线性增长 |
| 同形态 2 处且**颜色/尺寸已分叉** | 抽共享件（按分叉处理，优先级提高） | 分叉是 bug 温床：同一房间号胶囊在 core 与 demo 呈两种视觉 |
| 同形态 2 处且完全一致 | 可抽可不抽；先记录 | 收益低，改动面可能大于收益 |
| 已有件但 0 业务引用 | **先裁决去留**：补齐采用 or 删除 | 零引用组件是负债（`BaseButton` 案例） |
| 已有件但漏用 N 处 | 改用，不新建 | 见 §2 第 2 步 |

## 3. 新建组件的契约

### 3.1 命名

| 场景 | 命名 | 例 |
|---|---|---|
| L4 通用原子件 | `Base<Thing>` | `BaseSection`、`BaseConfirmDialog` |
| L5 域内组合件 | `<Domain><Thing>` | `GameReadyRoomCodeChip`、`RoomBottomActionBar` |
| 业务专属私有件 | `_` 前缀，留在模块内 | `_ReadyAvatar`（若确实私有） |

> 同一职责不允许两个名字表达同一形态（`BaseButton` 与 `EmphasisButton` 是现存反例，见 §5）。

### 3.2 参数化（硬约束）

| 项 | 规则 |
|---|---|
| 颜色 | 走 `ColorStrategy` / `Theme.of(context).colorScheme`；确有豁免（如棋盘识别色、纸质书视觉）走 Eb05 豁免登记并说明理由。**禁止裸写 `Color(0x…)`**（`lib/design_tokens/color/` 下的 token 定义除外） |
| 圆角 / 间距 | 走 `AppRadius` / `AppSpacing` / `AppBorderRadius`（`lib/design_tokens/`） |
| 透明度 | `withValues(alpha:)`，不用 `withOpacity` |
| 文本 | **默认文案必须本地化**。历史教训：`BaseConfirmDialog` 曾默认英文 `'Delete' / 'Cancel'`（2026-10-23 已改为中文「确认/取消」，`base_dialog.dart:20-21`），7 个既有调用点无一传 `cancelLabel`，英文按钮差点随推广扩散。新组件默认文案一律中文，具体动作词由调用方传参 |
| 策略解析 | 「取 ThemeExtension → 回落 DefaultColorStrategy」这段样板目前复制在 7 个 atomic 组件里，应抽为扩展/mixin；新组件不得再复制第 8 份 |
| 尺寸常量 | 组件自身提供默认参数，但不得写死业务尺寸 |

### 3.3 结构

- **单一职责**：一个组件一种形态。组合优先用组合 + 插槽（`child` / `slots` / `actions`），不要用参数膨胀出一个「万能组件」。
- **插槽优先于 builder**：FR 已有先例 `GameLobbySlots`（`lib/core/game_kit/lobby/game_lobby_slots.dart`）——用具名插槽让调用方插入差异部分，而不是给共享组件塞 12 个可选参数。
- **可独立渲染**：组件不得隐式依赖业务全局状态；缺省参数下也必须能渲染出合理结果。
- **委托模式**：壳层管生命周期与骨架，游戏/业务差异走策略或插槽。FR 已验证此路（`GameLobbyPage` + `GameLobbySpec`：13 个游戏全部 spec 化接入）。

### 3.4 组件健康度

- **零引用 = 死代码**：新组件提交前必须确认至少有 1 个真实调用点；已有组件零业务引用时，要么补齐采用、要么删除，不允许长期挂着。
- 每次组件层改动后重跑引用计数（命令见 [[Ec02-组件现状与收敛路线]] §5）。

## 4. Review 验收清单

新增或改动 UI 组件时逐条过：

- [ ] 先查过已有组件清单，确认不是重复造轮子
- [ ] 有更合适的已有件时，选择**改用**而非新建
- [ ] 组件落点符合 §1（通用件不在业务模块内，域内件不越层）
- [ ] 颜色走 ColorStrategy / ColorScheme；豁免项已按 Eb05 登记
- [ ] 圆角/间距走 `AppRadius` / `AppSpacing`
- [ ] 默认文案本地化
- [ ] 未复制 `_resolve(context)` 之类的策略样板
- [ ] 有真实调用点（不是「先放着以后用」）
- [ ] 未把业务规则/引擎代码抽进共享层
- [ ] 组件可独立渲染，无隐式全局依赖

## 5. 常见反模式（Top 5）

| 反模式 | 现象 | 后果 | 正确做法 |
|---|---|---|---|
| **组件建了没人用** | `BaseButton` 零业务引用，而实际用的是 `EmphasisButton` | 组件层持续空转，参考者无从判断该用哪个 | 每次新增组件必须带调用点；已有零引用件先裁决去留 |
| **同形态各自实现且已分叉** | demo 手写房间号 chip 用皮肤色，core 用 `colorScheme` | 同一 UI 在应用内两套视觉；demo 版不跟随主题 | 分叉按 bug 优先级处理，先统一色源再谈抽象 |
| **在业务模块里造通用件** | `ios_dialog.dart`（309 行通用弹窗套件）寄居 `gallerymanage` | 别的模块要么重复写、要么反向依赖业务模块 | 通用件下沉到 L4/L5，模块只消费 |
| **把策略化差异塞进共享组件** | 共享组件 12 个可选参数，调用点只传其中 3 个 | 参数膨胀，调用点难读，改动面变大 | 差异走插槽或策略对象（`GameLobbySlots` 先例） |
| **按旧 `// Layer N:` 注释推断依赖** | 层号标注在 ColorStrategy 上不一致 | 误以为 L4 可依赖 L6，引入反向依赖 | 依赖方向按 §1 表判断，注释仅作参考 |
