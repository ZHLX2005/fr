# Ec02 — 用色审计（SOP）

> **E 序列索引**：[[E00-UI骨架地图]] —— 动作层（改骨架时才读：扩角色 / 审计 / 豁免 / 批量治理）。
>
> **何时读**：评审某个目录的用色、清点残留裸 hex、给残留定归属、或批量治理前摸底时。
>
> 红线：`lib/` 新增代码禁止裸 hex —— 走 scheme / 6 通道，或写豁免注释说明业务理由（《Ea01 主题与token地图》§6）。

## 1. 审计工作流（五步）

1. **通道用量扫描**（谁在用哪些通道，按目录/文件计数）：

```bash
# 按目录统计各通道使用文件数
for d in lib/core lib/lab lib/screens lib/services lib/core/ui; do
  echo "$d: Theme.of=$(grep -rl 'Theme.of(context)' "$d" --include='*.dart' | wc -l) | colors=$(grep -rl 'context\.colors\b' "$d" --include='*.dart' | wc -l) | board=$(grep -rl 'context\.boardColors' "$d" --include='*.dart' | wc -l) | chess=$(grep -rl 'context\.chessColors' "$d" --include='*.dart' | wc -l) | tetris=$(grep -rl 'context\.tetrisColors' "$d" --include='*.dart' | wc -l) | team=$(grep -rl 'context\.teamAvatar' "$d" --include='*.dart' | wc -l) | sudoku=$(grep -rl 'context\.sudokuColors' "$d" --include='*.dart' | wc -l) | torch=$(grep -rl 'context\.torchProtect' "$d" --include='*.dart' | wc -l)"
done
```

2. **残留 hex 清点**（总量 + 按文件归属）：

```bash
# 残留硬编码 hex 总数（排除 token 定义层）
grep -rn "Color(0xFF" lib/ --include="*.dart" | grep -v "lib/core/theme/" | wc -l

# 按文件看残留归属
grep -rn "Color(0xFF" lib/ --include="*.dart" | grep -v "lib/core/theme/" | cut -d: -f1 | sort | uniq -c | sort -rn
```

3. **热点定位**（单文件 `Theme.of(context)` 出现次数，code review 优先扫高分文件）：

```bash
grep -ro "Theme.of(context)" lib/ --include="*.dart" | cut -d: -f1 | sort | uniq -c | sort -rn | head -20
```

4. **逐条归属判定**：对残留清单逐条看源码，按 §2 判定表归类——**每一处必须能归入五类之一**，归不进的就是待整改项。

```bash
# 列出每处残留（逐条判定用）
grep -rn "Color(0xFF" lib/ --include="*.dart" | grep -v "lib/core/theme/"
```

5. **验证**：任何整改后必须

```bash
flutter analyze --no-pub        # 0 error
flutter build apk --debug       # 原生/主题改动必须过 build
flutter test test/core/theme/chess_color_strategy_test.dart   # chess 通道回归
flutter test test/lab/tetris_lua/                             # tetris 特例回归（本地 .gitignore）
```

> 表格与计数都是**某次审计的快照**（历次快照归档在 `docs/architecture/theme-channel-audit.md` §9），代码持续漂移——**引用任何数字前先现场重跑本节命令**，不要拿历史快照当现状。

## 2. 残留 hex 归属判定表

对 §1 第 4 步列出的每处残留，按顺序问：

| # | 这处 hex 在哪层？ | 归类 | 处理动作 |
|---|---|---|---|
| 1 | `lib/design_tokens/`（palettes/torch/sudoku/tetris/team/chess） | **token 层** | 无需处理——token 文件本身就是色值真源 |
| 2 | 业务模块内成套令牌类（如 `BoardThemeData` / `DraughtsBoardPalette` 独立预设系统） | **S 独立令牌系统** | 保留；类注释逐项登记（对齐 surround_game / reversi / xiangqi / draughts 先例）。是否并轨 strategy 属架构议题，见 theme-channel-audit §9.9 |
| 3 | 语义要求颜色跨主题稳定（品牌 / 国际识别色 / 纸质书视觉 / 医学解剖 / 评级奖励渐变…） | **E 豁免** | 必须带 `主题豁免` 注释说明业务理由；没有注释的补注释。新增特例走《Ec03 特例豁免》 |
| 4 | 属于已建特例 strategy 的域（tetris 方块色 / teamAvatar 头像色） | **特例 strategy** | 色值应集中在 `lib/design_tokens/color/{tetris,team}.dart` native const 表，调用方零裸 hex；发现调用点散写 → 迁进 token 表 |
| 5 | 以上都不是（普通 UI 用色却写死 hex） | **未分类 = 待整改** | 走《Ec01 扩展SOP与迁移》§4 迁移 SOP 迁到正确通道 |

> 判定歧义时：第 2 类与第 3 类的边界是「**成套系统 vs 单点语义**」——一整套多角色的预设系统走 S（独立令牌类 + 类注释），单个语义色走 E（行内豁免注释）。

## 3. 目录推荐配色策略速查

新写/评审某目录的 UI 时，按目录类型对号入座：

| 目录类型 | 推荐通道 | 理由 |
| --- | --- | --- |
| 业务壳层（profile/chat/setting） | `Theme.of(context).colorScheme.X` + `context.colors` | 跨主题一致性高 |
| 棋盘/棋类游戏（gomoku/reversi/jungle） | `context.boardColors` | 棋子黑白关系 + 棋盘环境独立 |
| 国际象棋 | `context.chessColors` | 两色格 + 选中/将军/升变（v6.2.1 新通道） |
| 俄罗斯方块 | `context.tetrisColors` | 7 方块识别色锁定，玩家靠颜色识别 |
| 团队卡头像 | `context.teamAvatar` | 6 头像色锁定，色 = 身份 |
| 护眼灯 | `TorchProtectColorStrategyExtension`（**无 context 入口**） | 4 个 UI 角色跟主题联动；10 预设色由 `torch.dart` 直连消费 |
| AI 聊天/笔记/阅读 | `Theme.of(context).colorScheme.X` + `AppColorsExtension.category` | 文本/分类场景 |
| 计时/专注（zen 风） | `Theme.of(context).colorScheme.X` + sage 家族（豁免） | 与 zen 主题呼应 |
| 调试/诊断页 | `Theme.of(context).colorScheme.X` | 无视觉风格诉求 |
| 自定义数据色（站点/品牌） | **硬编码豁免** + `主题豁免` 注释 | 数据持久化属性 |
